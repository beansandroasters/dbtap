[English](validation.md) | 日本語

## DB ログの復元率と時刻

2026-11-14、8 vCPU の同一ホスト上の PostgreSQL **17.12** / MySQL **8.4.13** で実施しました。各 6 接続・120 操作、並行する送金・参照・エラー・プリペアド実行を含みます。比較に使った通信記録はいずれも欠落 0 バイトです。元データと計算済みの数字は [実測 JSON](log-validation-20261114.json) に残しています。

| 負荷 | 通信の単位数 | 通信の SQL 実行数 | ログで対応した実行 | 再生可能 | 最終状態 |
|---|---:|---:|---:|---:|---|
| PostgreSQL・COPY なし | 2,742 | 2,664 | 2,664 (100%) | 2,664 | 一致 |
| PostgreSQL・COPY あり | 2,741 | 2,664 | 2,664 (100%) | 2,643 (99.21%) | bulk だけ 420 行不足 |
| MySQL | 3,660 | 1,942 | 1,942 (100%) | 1,942 | 一致 |

「最終状態」は accounts の残高と orders の業務列、PG の bulk を直接比較したものです。並行 INSERT の採番 ID は参考値として分けています。通信の単位数と SQL 実行数は一致しません。PG の COPY なしでは実行のない単位が 105 件、複数実行を含む単位が 27 件、MySQL では SQL 以外のコマンドが 1,718 件あります。

照合は同じセッション内の順序を使い、PG は SQL とパラメータ、MySQL は文の形と値キーを比べています。MySQL の値キーは位置を保持しないため、この照合だけで任意の入力の意味が一致したとは判定できません。上の 100% はこの負荷での対応率です。PG のエラーは 35 実行で所要時間不明、MySQL は 57 実行でエラー番号まで残りました。

次は **ログ − 通信** の時刻差です。負ならログのほうが早く、同一ホストなので時計のずれは含みません。PG は COPY なしで、通信側が 1 実行だけの単位かつ所要時間がある 2,575 件、MySQL は 1,942 件を比べています。

| 時刻差(ms) | p50 | p95 | 最小 / 最大 |
|---|---:|---:|---:|
| PG 開始 | -0.366 | +0.145 | -0.957 / +2.730 |
| PG 終了 | -0.586 | -0.113 | -5.173 / -0.053 |
| MySQL 開始 | +0.066 | +2.768 | +0.032 / +14.720 |
| MySQL 終了 | -0.022 | +0.032 | -10.003 / +0.853 |

DB の実行時刻と、ネットワーク上で要求・応答を観測する時刻は異なります。PG の ms への丸め、parse / bind の範囲、DB 内の待ちや応答送信も差に含まれます。ログ由来の時刻を通信と同じ精度だとは扱えません。

| ログの量 | 対象セッション分(圧縮前) | 1 SQL 実行あたり | 変換後のジャーナル |
|---|---:|---:|---:|
| PG・COPY なし | 1,237,721 B | 464.6 B | 63,385 B |
| MySQL | 2,113,852 B | 1,088.5 B | 63,880 B |

parse / bind や管理コマンドもログ量に含めています。文の長さとプリペアドの使い方で比率は変わります。

### ログを有効にしたときの影響

同じ PostgreSQL 17.12、pgbench の TPC-B 風負荷・16 接続・prepared・スケール 10 で、30 秒ウォームアップ後にログなし / ありを 30 秒ずつ 3 組測りました。DB と負荷は同一の 8 vCPU ホストです。測定中はほかの負荷テストやビルドを実行していませんが、ホストを専有して他プロセスの負荷まで統制した測定ではありません。

| 組 | ログなし TPS | ログあり TPS | ありの CSV 増加量 |
|---|---:|---:|---:|
| 1 | 3,414.1 | 3,587.5 | 448,460,654 B |
| 2 | 3,242.0 | 3,191.3 | 399,475,757 B |
| 3 | 3,625.7 | 3,221.2 | 404,059,695 B |
| 平均 | 3,427.3 | 3,333.3 | — |

平均の差は **-2.74%** でした。ただし組ごとの振れがあり、一定のオーバーヘッドを示したものではありません。CSV は **約 4,167〜4,182 B/トランザクション、13.3〜14.9 MB/秒** 増えました。この量は接続・切断と parse / bind / execute を含み、ログなしの測定中の CSV 増加は 0 B でした。ログの書き込み先が追いつかない環境では、この測定より影響が大きくなりえます。

実行スクリプトは `e2e/logging_bench.py`、6 回の pgbench 出力と設定・計算値は [実測 JSON](log-validation-20261114.json) の `logging_benchmark` にあります。集計対象は完了した 6 回の測定です。

公式資料: [PostgreSQL 17 のログ設定と CSV の列](https://www.postgresql.org/docs/17/runtime-config-logging.html)、[MySQL 8.4 のスローログ](https://docs.oracle.com/cd/E17952_01/mysql-8.4-en/slow-query-log.html)、[MySQL の GLOBAL / SESSION 変数](https://docs.oracle.com/cd/E17952_01/mysql-8.4-en/using-system-variables.html)。portal 継続と採番用メタデータは [PG17 の実装](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/tcop/postgres.c)・[MySQL 8.4 の実装](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/sql/log.cc)も確認しました。

## 通信経路の性能測定

8 vCPU の EC2 1 台に DB(Docker)・負荷・dbtap を同居させた測定です。[再現手順](../e2e/README.ja.md)を参照してください。

**混合負荷**(PostgreSQL 17 と MySQL 8.4 に各 6 接続。送金のトランザクション、参照、一意制約違反、非決定的な文、COPY、パイプライン、プリペアドステートメント。約 10 秒・6,401 単位。既定の設定で 4 回)

| 項目 | 結果 |
|---|---|
| 取りこぼし | 0 バイト |
| 結果の比較 | 一致 98.6% / 非決定的 1.4% / 重なっていた読み取り 0〜3 件 / 本物の食い違い 0 件 |
| 入れ替わり・待ち切れず | 入れ替わり 0〜1 件(問い合わせで解けた)/ 待ち切れず 0 件 |
| 予定時刻からの遅れ | p50 0.02ms / p95 0.07〜0.15ms(`--order table` では p95 0.1〜0.5ms) |
| 再生後のデータ | 元と一致(採番を除く。[制約](../README.ja.md#制約)を参照) |

途中から拾った接続だけの記録、その 4 倍速での再生(MySQL は TLS)、2 つのジャーナル + 2 プロセスからの再生でも、再生後のデータは元と一致しました。VXLAN に包んだ通信は、ファイル経由でもライブでも、包む前と同じ 6,401 単位に復元できました。

対応する認証方式と TLS の条件は [セキュリティ](../SECURITY.ja.md)を参照してください。MySQL 8 系のクライアントがクエリ属性を使っている接続は、対応していない再生先(MariaDB)には再生できず、その旨を報告して止めます。

**pgbench**(TPC-B 風、32 接続、プリペアド、スケール 10。10 行の branches を全接続が取り合う、ロック競合の極端な例)

| 項目 | 結果 |
|---|---|
| 通信の記録が元の負荷に与える影響 | 記録なし平均 4,166 TPS / 記録あり平均 4,162 TPS(3 回ずつ交互。差はばらつきの範囲) |
| 記録の CPU | 10 秒・63 万パケット・27.6MB に対して 0.41 秒(1 コアの約 4%)。取りこぼし 0 |
| 要約(`inspect`) | 30 秒・727,200 単位で 2.7 秒、最大メモリ 6.7MB |
| 再生のメモリ | 30 秒・727,200 単位で、`--order table` は最大 164MB、既定の `row` は 269MB。記録全体は保持しないが、先読み・接続数・単位サイズに依存する。接続数・要求サイズが異なる負荷への上限値ではない |
| 再生の CPU | 10 秒・319,352 単位で約 14 秒(user 6.1 / sys 8.3) |

飽和した 10 秒の記録(4,568 TPS・319,352 単位)を、3 つの方式で 2 回ずつ交互に再生した結果です。どの回も本物の食い違い 0 件、入れ替わり 0 件で、再生後のデータは元と一致しました(pgbench の更新は足し算なので、順序が入れ替わっても最終結果は変わりません。`time` で崩れるのは途中の読み取りで、別の記録では「重なっていた読み取り」が 26〜120 件出ました)。

| `--order` | 再生にかかった時間 | 記録(10.0 秒)との差 |
|---|---|---|
| `table` | 12.6 秒 / 12.8 秒 | +26〜28% |
| `row` | 11.9 秒 / 11.7 秒 | +16〜19% |
| `time` | 11.0 秒 / 11.0 秒 | +9% |

### AWS 上での通し検証

東京リージョンの閉じた VPC(インターネットゲートウェイも NAT もなし)に、Aurora PostgreSQL 16.15(db.r6g.large)、RDS MySQL 8.0.46(db.m6g.large)、負荷と再生用の EC2(c6i.xlarge)、ミラーの受け側の EC2(c6i.large)を置いて確かめました(2026-11-13)。テンプレートと手順は `aws/` にあります。

| 確かめたこと | 結果 |
|---|---|
| DB のネットワークインターフェイスをミラー元にできるか | Aurora のインスタンスも RDS MySQL も、セッションを張れた |
| ミラー越しの記録は欠けないか | 負荷側で直接取った記録と、3 回とも完全に一致(毎秒 2.9 万トランザクションの読み取り: 467,239 パケット・233,496 単位。書き込みあり: 287,341 パケット・143,387 単位。どちらも欠落 0) |
| 大きなパケットは切り詰められるか | 切り詰められる。クライアントの MTU を 8951 にすると解消する([通信の取り込み](capture.ja.md)を参照) |
| クローンと特定時点復元へ TLS で再生できるか | `--tls require --tls-ca`(RDS の CA バンドルで証明書を検証)で、Aurora のクローンと RDS MySQL の特定時点復元へ再生できた |
| 再生後のデータは元と一致するか | Aurora は 8 項目すべて、RDS MySQL は残高と注文の中身が一致(採番 ID を除く) |

書き込みのある負荷を 2 種類流しました。

| 負荷 | `--order` | 結果の比較 | 入れ替わり | 予定時刻からの遅れ p50 / p95 | 再生にかかった時間 |
|---|---|---|---|---|---|
| 飽和: pgbench 16 接続(961 TPS)+ MySQL 8 接続。143,387 単位 | `table` | 本物の食い違い 0 件 | 4 件 | 5.6 秒 / 7.6 秒 | 28.2 秒(記録 20.1 秒) |
| 余裕あり: pgbench 16 接続を毎秒 300 に制限。62,642 単位 | `table` | すべて一致 | 35 件 | 5.3ms / 298ms | 31.9 秒(記録 31.6 秒) |
| 同上(同じ記録を別のクローンへ) | `row` | すべて一致 | 0 件 | 0.04ms / 2.8ms | 31.9 秒 |

余裕のある負荷を既定の `row` で再生したときの応答時間は、記録が p50 0.133ms / p95 3.31ms / p99 5.57ms、再生が p50 0.158ms / p95 3.24ms / p99 5.18ms でした(記録は DB のインターフェイスで、再生はクライアント側で測っているので、p50 の差には片道分の往復時間が入っています)。

飽和した負荷を `row` で再生した結果は、AWS 上では取っていません。

AWS の測定は 2026-11-13 の構成によるものです。現在の `aws/verify.yaml` 全体のデプロイ成功を示すものではありません。AWS レポートは [aws/results](../aws/results/) にあります。

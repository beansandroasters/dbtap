# 比較・レポート

[English](reporting.md) | 日本語

次は通信由来の記録を再生したときの出力例です。

```
-- Result comparison --
     6309   98.6%  Observed fields match
       88    1.4%  Non-deterministic statement (content difference ignored)
        4    0.1%  Read overlaps a conflicting write (visibility undetermined)
Units with dependency waits: 55 / lock reversals released: 0 / causal timeouts: 0

-- Response time (ms) --        p50       p95       p99       max      mean
Captured                         0.150     1.491     4.162    93.591     0.488
Replayed                         0.186     1.753     4.260    95.530     0.520
Send lag                  0.018     0.274     1.229    36.821     0.093
Dependency wait                  0.266    10.093    22.807    36.802     2.192
```

| 判定 | 意味 |
|---|---|
| 観測した項目が一致 | 通信由来では行数・影響行数・行の内容・エラーが同じ。ログ由来では `compared` に示す項目だけが同じ |
| 非決定的な文 | 内容は違うが、`now()` や乱数など実行のたびに値が変わる文 |
| 競合する書き込みと重なっていた読み取り | 記録の上で、同じテーブルへの書き込みの最中に走った読み取り。相手の変更が見えていたかは通信からは決まらないので、再生の誤りとは言えない |
| 行の並びだけ違う | 行の集合は同じ。ORDER BY のない結果でよく出る |
| 内容が違う / 行数が違う / 影響行数が違う / エラーの有無・種類が違う | 本物の食い違い。再生先のデータが記録開始時点と違う、順序が保てなかった、などを疑う |

**予定時刻からの遅れ**は、実際の送信が予定からどれだけ遅れたかです。再生先の応答、依存関係の待ち、負荷生成側の CPU・ネットワーク・出力待ちが影響します。DB のリソース使用量そのものを表す値ではありません。記録でロック待ちをしていた書き込みは、先にロックを取った相手が終わるまで投げるのを待つので、その分は遅れとして出ます(上の例では、遅れの最大 36.8ms が「前後関係の待ち」の最大とほぼ同じです)。

**ロックの順序が入れ替わって先へ進んだ単位**は、再生先でロックの取得順が記録と入れ替わり、待っても終わらないと分かって待つのをやめた回数です。**待ち切れずに投げた単位**は、上限(`--causal-timeout-ms`、既定 1 秒)まで待っても終わらなかった回数で、0 でなければ、そのとき誰を待っていたかが標準エラーとレポートに出ます。

応答時間は分布(区間の幅は値の約 3%)として集計しているので、分位点にはその程度の丸めがあります。記録は取り込み口(ネットワーク上)で、再生は dbtap の中で測っています。測る位置が違うので、微小な差は測定位置と時計の精度を考慮して解釈してください。DB ログ由来では時刻の丸めと計測区間も異なります。

## 終了コードと自動判定

`dbtap replay` の終了コード 0 は全単位の成功・一致を保証しません。接続不能や単位の実行失敗はレポートの `failed`、未再生は `skipped`、結果差は `verdicts` を確認します。samples の `end` も処理完了を表し、全要求の成功ではありません。

- `ran` / `failed` / `skipped` / `elsewhere`: 実行した数、実行処理の失敗、再生不可、別 shard の担当。
- `compared`: エラー・行数・影響行数・内容・応答時間を比較できた単位数。
- `latency_captured` / `latency_replayed`: 観測できた応答時間の分布。
- `lag` / `order_wait`: 予定時刻からの遅れと依存関係を待った時間。

記録と同じ DB エラーなら比較は Match になります。Locust / JMeter / k6 の要求失敗率は実際の DB エラーを数えるため、比較の一致率とは異なります。

`dbtap report` はレポートを加算します。異なる実行や重複 shard の混在を検査する機能はありません。共通 run-id と全 shard を検査して結果を統合する場合は、[samples の変換器](../integrations/README.ja.md)を使います。

通常のレポートと `inspect --jsonl` は SQL や値を含みます。外部ツールへ時系列を渡す場合は `--samples` を使い、公開前に内容を確認してください。
